DESIGN (proposals; owner decisions marked)
A. Separate jobs: (1) sync + escalation, every 2 min, unchanged; (2) closure job, every 5 min, database only, no OpsGenie calls; (3) reconciliation against OpsGenie, later, throttled. Start with per-job locks, timeouts and concurrency caps; a second container only if measurements show contention.
B. Closure rule: a Closed notice marks the matching Open incident for closure when the notice's own createdAt is later than the Open's createdAt. If no newer Open for the same problem exists 15 min after the notice, resolve, with resolved_at = the notice time. A newer Open within the hold reopens the same incident. OpsGenie live status is not used for Zabbix closure. Creation also skips an Open when a later Closed already exists.
C. Status model (owner fine with either; confirm before build): Option A = new MARKED_FOR_CLOSURE status, counted as closed in dashboards until reopened (recommended). Option B = resolve immediately under its own resolution_type and reopen within 15 min using reopened_at/reopen_reason. For A: first update every status reader (no behaviour change; audit before and after), then add the job in dry-run.
D. Audit trail: an event table written at each decision (create, skip, mark, resolve, reopen, suppress) with the reason and evidence, plus a UI search by alert title showing current status, MTTR and history. IDs only for drill-down. Retention to decide.
E. Recurrence report (reporting only; the agent takes no action on it): group Open alerts by alert title with status and severity tags stripped (start simple; no host/check parsing); counts per week and month with trend; headline = raw Open alerts per title so suppression does not hide a problem, incident counts beside it. A monthly rollup table (one row per title per month) to outlive the 30-day retention. Enhancements only on request. Suppressed alerts count toward recurrence (recommended; owner to confirm). The recurrence_count column is meaningless (increments every cycle); nothing should read it.
F. Reconciliation: intent is to detect incidents resolved outside the pipeline using the bracket tag and the status. Today an [Open]/[Critical]/[Warning] title returns "open", so OpsGenie is never asked, and the stored title can never say closed. Redesign after the closure job. Owner decides which signals count as resolved outside the pipeline (OpsGenie status, current bracket tag, or both) using real counts.
G. Scope boundary: the incidents table is the contract with other agents. Write a short contract note (what a row means and when status changes) once the closure rule exists.
