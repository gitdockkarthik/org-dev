AgentsIQ Studio

A multi-domain AI platform that brings intelligent agents to your operations team. Each agent specialises in a specific domain — alert noise detection, cloud cost analysis, infrastructure health — and provides an AI chatbot, dashboard, and reports powered by your real data.

Access

The platform is available at studio.agentsiq.net. Access is protected by Cloudflare Access — enter your email address and you will receive a one-time verification code. No password to manage.

To deploy your own instance, you need exactly two environment variables set before the application starts. Everything else is configured through the Setup Wizard and individual agent Settings pages.

Minimum Environment Variables

VariableDescription
DATABASE_URL Required. PostgreSQL connection string. Set via .env or your platform dashboard. The database must exist before the application starts — this cannot be configured through the UI.
ENCRYPTION_KEY Required. Fernet symmetric key used to encrypt secrets at rest. Generate once with:
python3 -c 'from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())'
All services in the same deployment must share the same key. Never change this after initial setup — it will render all stored secrets unreadable.
⚠
Do not set PORT manually. Railway, ECS, and Kubernetes inject PORT automatically. Setting it in your environment will conflict with the platform's port binding.

After providing these two variables, open the platform URL and the Setup Wizard will guide you through the remaining configuration in under two minutes.

Navigation

Each agent card on the catalogue shows the agent's name, description, model version, and quick action buttons. Use the search bar to filter agents by name, slug, or description — filtering runs locally with no server round-trip. The catalogue updates automatically when agents are published or deprecated.

Agent Catalogue

Published agents appear as cards. Each card's accent colour is derived deterministically from the agent's slug — the same agent always shows the same colour across browsers and sessions. The agent count shown top-right of the catalogue updates in real time as agents are published or deprecated.

Click Chat to open the agent's conversation interface. The other buttons open the agent's workspace pages — dashboards display pre-computed analytics, reports show uploaded or synced data sets, and settings control the agent's data source.

Chat Interface

The left sidebar shows four pieces of information: the agent name, the model currently in use, your session ID, and the current data context — what data the agent is working with and key metrics derived from it.

Type your question in the input box at the bottom and press Enter to send. The agent responds with analysis, structured tables, and actionable recommendations. Markdown formatting — headers, bold, code blocks, and tables — is rendered inline.

Ask follow-up questions naturally. The agent retains context within a session: you can reference earlier parts of the conversation without repeating background.

Sessions

Click New Session in the sidebar to start a fresh conversation. The previous session is preserved in the database and can be resumed by navigating back with the same session ID. Sessions are identified by a UUID stored in sessionStorage — refreshing the page resumes the same session; closing the tab and reopening starts a new one.

Operator Guide

Operators manage the platform via the Admin link in the top bar. The admin console has two tabs: Agents and Platform.

Agents Tab

Lists all registered agents with status filters: All, Draft, Published, Deprecated.

  • Deprecate — removes an agent from the catalogue without deleting its registration or chat history. The agent moves to the Deprecated tab and can be re-published at any time.
  • + Register Agent — opens the registration form. Fill in the name, slug, description, invoke URL, and model. The agent starts in Draft status.
  • Publish — makes a Draft agent live in the catalogue immediately.
📋
The slug is the permanent identifier for an agent. It is used in URLs, the invoke path, and the database. Choose it carefully — changing it after registration requires re-registering the agent and migrating any stored sessions.

Platform Tab

The Platform tab shows the current state of the backend configuration:

  • Anthropic API — shows Connected if the API key is present and valid, Not configured if missing.
  • Model in use — the Claude model used for direct invocations.
  • Published agents — count of agents currently visible in the catalogue.
  • Platform version — the backend release version.

The Test Connection button in the Edit Platform Config section tests a new Anthropic API key without saving it. Changes made here apply immediately — the backend cache is updated in memory without requiring a redeployment.

Agent Settings

Each agent has a Settings page accessible from its card (Settings button) or from the sub-navigation bar within the agent workspace. Settings are stored encrypted in the database and survive restarts — there is no need to reconfigure after upgrades or redeployments.

Alert Analyser

Choose the source for alert data:

  • File Upload — upload a CSV or JSON export from OpsGenie via the Reports page. The file is parsed on upload and stored in memory for the session.
  • OpsGenie / JSM API — enter your Cloud ID, email address, and API token. The agent calls the JSM Ops API directly and retrieves the last 100 alerts. Click Save & Sync to pull data immediately. Subsequent syncs can be triggered from the Settings page at any time.
  • Synthetic Data — generates a realistic set of OpsGenie-formatted alerts for demonstration. No credentials required.

Credentials (API token, Cloud ID) are encrypted using the deployment's ENCRYPTION_KEY before being written to the database. They are decrypted in memory at runtime and never returned to the browser.

Sync Schedule

Configure how often the agent automatically pulls fresh data from OpsGenie. Options: Disabled, Every 15 min, Every 30 min, Every hour, Every 6 hours, Every 24 hours. Set to Disabled if you prefer to sync manually. The last synced time is shown below the dropdown.

Noise Detection Tuning

Two thresholds control how alerts are classified as noise:

  • Repeat threshold — alerts firing more than this many times in 1 hour are flagged as noise. Default: 3.
  • Auto-close threshold — alerts that auto-close in fewer than this many seconds are flagged as noise. Default: 300 seconds (5 minutes).

Tune these to match your organisation's alert patterns. Changes take effect immediately on the next sync. All settings are persisted to your database and survive restarts.

CUR Analyser

Choose the source for AWS cost data:

  • File Upload — upload an AWS Cost and Usage Report CSV export via the Reports page. The file must use the standard CUR column schema.
  • Synthetic Data — auto-generates a realistic CUR dataset with multiple services, regions, and accounts. No AWS credentials required.

AWS Cost Explorer API integration is planned for Phase 2. For now, export your CUR data from the AWS Billing console and upload it via the Reports page.

Infra Health Check

The Settings page for Infra Health Check is read-only. It shows the agent's current health status, model version, and invoke URL. No configuration is required — the agent's health data is built in, covering five services: api-server, database, cache, queue, and cdn.

Client Delivery & Deployment

AgentsIQ agents are delivered as standalone plugin repositories. Each plugin is self-contained and deployable on any platform that runs Docker — Railway, ECS, Fly.io, or a bare VM with Docker Compose.

Required Environment Variables

Only two variables must be set before the application starts. Everything else is configured through the Setup Wizard or agent Settings pages.

VariableSet viaNotes
DATABASE_URL .env or platform dashboard PostgreSQL connection string. The database must exist before startup. Cannot be set through the UI.
ENCRYPTION_KEY .env or platform dashboard All services must share the same key. Generate once — never rotate after data has been written.
PORT Auto-injected Never set manually. Railway, ECS, and Kubernetes inject this at runtime.

The following are configured through the UI after first start:

  • Anthropic API Key — entered in Setup Wizard Step 1, stored encrypted in the platform_config table.
  • Platform API Key — auto-generated in Setup Wizard Step 2, stored encrypted in the platform_config table. This key secures all communication between the portal and the backend API — every portal request includes it as an X-API-Key header. Users never interact with it directly. The portal fetches this key automatically from the backend at load time via GET /api/platform/bootstrap, so wizard-generated keys work immediately without any environment variable changes.
  • OpsGenie credentials — entered in Alert Analyser Settings, stored encrypted in the agent's agent_config table.
  • Data source preferences — configured per agent in their respective Settings pages.

Deployment Steps

1
Clone the agent repository
Each agent is delivered as a standalone repo. Clone it to your deployment environment.
2
Copy .env.example to .env
The example file documents every variable. You only need to fill in two.
3
Set DATABASE_URL and ENCRYPTION_KEY
These are the only variables that cannot be set through the UI. Generate the encryption key with the command documented in .env.example.
4
Run docker compose up
Starts all services. The backend creates the database schema automatically on first start.
5
Open the portal in your browser
The platform detects that no Anthropic key is configured and redirects automatically to the Setup Wizard.
6
Complete the Setup Wizard
Takes approximately two minutes. Enter and test your Anthropic API key, then copy the auto-generated Platform API Key. Both are saved encrypted to the database.
7
Configure each agent's data source
Go to each agent's Settings page and select your data source. For Alert Analyser with OpsGenie, enter your Cloud ID, email, and API token, then click Save & Sync.
8
Data is live
The agent populates its dashboard and is ready to answer questions. Open the catalogue and click Chat.
💡
To register a new agent with the platform, click + Register Agent in the Admin console and fill in the manifest details. No API calls, no file editing, no restarts required.

Known Limitations

  • Agent configuration requires DATABASE_URL for persistence. If an agent container restarts without DATABASE_URL configured, any previously saved settings (OpsGenie credentials, data source preference) will not be restored.
  • No scheduled auto-sync. Alert data must be manually synced via the Alert Analyser Settings page. Automatic scheduled sync is planned for Phase 2.
  • AWS Cost Explorer API integration is planned for Phase 2. CUR data must currently be exported from the AWS Billing console and uploaded manually via the Reports page.

Agent Development

Build a new agent by copying the agents/agent-template/ folder. The template is self-contained — it has no dependency on the monorepo's shared/ package and can be extracted and delivered as a standalone repository to clients.

Invoke Contract

Every agent exposes exactly two HTTP endpoints:

Method + PathDescriptionAuth
GET /healthReturns {"status":"ok","agent":"<slug>"}None
POST /invokeAccepts InvokeRequest, returns InvokeResponseNone (backend handles auth)

The POST /invoke body:

InvokeRequest
session_id
string
required — UUID v4. Groups messages into a conversation.
user_message
string
required — The user's current message.
context
dict
optional — Arbitrary key-value pairs injected into the system prompt. Use for tenant data, loaded report content, or session metadata.
history
list
optional — Previous messages as [{"role":"user"|"assistant","content":"..."}]. The orchestrator loads DB history automatically; standalone agents use this field directly.

The response must contain a response string and a metadata dict. The template returns {"tokens_used": N} in metadata.

Tools

Define tools in the tools/ folder by subclassing ToolExecutor:

python — tools/my_tool.py 
from typing import Any
from tools.base import ToolExecutor

class MyTool(ToolExecutor):
    name = "my_tool"
    description = "What this tool does, written for Claude to understand."
    input_schema = {
        "type": "object",
        "properties": {
            "query": {"type": "string", "description": "The input to process."}
        },
        "required": ["query"],
    }

    async def execute(self, **kwargs: Any) -> str:
        query = kwargs["query"]
        # ... perform work ...
        return "Result as a plain string."

Register tools in main.py:

python — main.py 
from tools.my_tool import MyTool
_runner = AgentRunner(tools=[MyTool()])

AgentRunner handles the multi-turn tool loop automatically. It runs until Claude returns stop_reason == "end_turn", executing each tool call and appending results before the next Claude turn.

Config Persistence

Add settings persistence using the agent_config database pattern — see alert-analyser for the reference implementation: models.py defines the agent_config table, database.py creates the async engine from DATABASE_URL, and routes_settings.py exposes GET /settings and POST /settings.

All secrets written through the Settings page are encrypted at rest using the deployment's shared ENCRYPTION_KEY. The encryption.py module in each agent handles encrypt/decrypt transparently — use is_secret_key(key) to determine which fields to encrypt before writing and decrypt after reading.

Declare your agent's configuration requirements in manifest.json — the platform reads this file during registration. Agents with a DATABASE_URL listed in env will have their agent_config table created automatically on first startup.

Self-Registration

If REGISTRY_URL and BACKEND_API_KEY are set, the agent calls POST /api/registry/agents on startup, resolves any 409 conflict by slug lookup, and publishes itself automatically. On Railway, set these two variables to the backend's public URL and API key — the agent will appear in the catalogue the first time it boots.

Alternatively, register manually via the Admin console + Register Agent button. Fill in the manifest details and click Publish now — the agent appears in the catalogue immediately.

⛔
Agents must be stateless. No in-memory session dictionaries, no file system writes, no database state beyond the agent_config settings table. Every request must be fully self-contained — all conversational context arrives through context and history. The platform's chat_messages table provides session persistence; agents should never need their own.
