Technical Architecture

Stack

  • Compute: FastAPI (Python 3.11) on Operative platform
  • Storage: PostgreSQL (metadata) + persistent volume (CUR files)
  • Query Engine: DuckDB (in-memory OLAP + file-path mode for large CUR)
  • Data Sources: CSV (.csv), Compressed (.gz, .zip), Parquet (.parquet), CUR 2.0 JSON tags blob
  • Enrichment: Inventory spreadsheet (XLSX) with ARN-tail matching

Dashboard Features

Six-tab interface for cost analysis and insights:

📌 Overview

KPI Summary: Total cost, row count, service breakdown. Daily Trend: Cost-per-day heatmap (13-week rolling window). Tag Coverage: AWS tag + inventory enrichment coverage %.

🏢 By Account

Cost-per-AWS-account with account name (from inventory) and environment context. Supports multi-account rollups and linked-account breakdowns.

🌍 By Environment

Cost-per-environment (prod/staging/nonprod/dev) with per-environment owner team and email. Inventory enrichment fallback when native tags absent.

⚙️ By Service

Top 15 services (EC2, S3, RDS, etc.) by cost, service category breakdown (Compute, Storage, Network, …), and owner team per service.

🏷️ Cost Centres & Tags

Cost by Product tag, Managed By (inventory), Customer tag, Cost Centre. Native AWS tags OR inventory fallback for untagged resources.

📈 Trends & Insights

Trends: MoM comparison by service. AI Insights: Claude-generated recommendations for tagging, cost optimization, and anomalies.

Inventory Enrichment

How It Works

When an inventory spreadsheet (XLSX) is uploaded alongside a CUR file:

  1. Parse inventory: Extract 9 join keys (account ID, resource ARN, resource type, …) and 10 enrichment fields (environment, customer, budget code, team, …).
  2. ARN-tail matching: Extract resource ID from CUR `lineItem/ResourceId` (e.g. `i-0123456789abcdef0` from `arn:aws:ec2:…`) and match against inventory.
  3. Account-level fallback: When resource not found, fall back to account-level enrichment (same environment/customer for all resources in that account).
  4. Cross-CUR reuse: Single inventory file enriches all uploaded CUR files; data persisted in Postgres and re-used across sessions.

Before/After Coverage

Before Enrichment

  • Environment: 45% coverage (native tags only)
  • Customer: 23% coverage (inconsistent tagging)
  • Budget Code: 18% coverage (legacy migration gap)

After Enrichment

  • Environment: 98% coverage (+53 pp)
  • Customer: 91% coverage (+68 pp)
  • Budget Code: 89% coverage (+71 pp)

Key Decisions

  • inv_* columns are primary tag source; CUR native tags are fallback only.
  • Account-level enrichment triggers only when resource-level match fails (reduces false-positive generalization).
  • Single inventory file applies to all CUR reports in the upload session (cost-efficient, user-friendly).
  • Registry persists via PostgreSQL across restarts; no re-upload required.

Key Business Outcomes

Dimension DBR (Legacy) CUR 2.0 (Modern) Operative CUR Analyser Support

File size 500MB–2GB/month 1–5GB/month (higher fidelity) ✓ File-path pipeline handles up to 10GB
Time-to-insight T+3 days (AWS processing) T+1 day ✓ On-demand upload; results in <60s
Inventory enrichment ❌ Not supported ❌ Not built-in ✓ Operative Innovation: XLSX inventory + ARN matching
AI-driven insights ❌ Manual analysis only ❌ Manual analysis only ✓ CUR Analyser agent: tagging recommendations, savings opportunities, untagged resource alerts

Impact Summary

  • Cost attribution accuracy: 45% → 98% coverage (inventory enrichment + AWS tags).
  • Time-to-action: 3 days (AWS DBR) → <60 seconds (on-demand upload + analysis).
  • Operational overhead: Manual pivot tables → automated dashboard with 6 cost dimensions + AI insights.
  • Compliance readiness: Supports cost-centre allocation audits, budget forecasting, chargeback automation.
