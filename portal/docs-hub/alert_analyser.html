🚨 Alert Analyser

OpsGenie alert triage, noise classification, suppression recommendations and incident ticket management

v1.2.0 Internal FastAPI + PostgreSQL Updated 2026-07-16 Port 8001

4 Data Sources

OpsGenie standalone, OpsGenie Cloud, Atlassian JSM, and file upload (JSON/CSV) for alert ingestion and enrichment.

Classification Engine

Rule-based noise detector scoring repeat rate, auto-close time, priority, and open duration to classify genuine vs noise vs suspect.

Incident Pipeline

Automated ticket creation and state progression: ESCALATED → INVESTIGATING → RCA_COMPLETE → REMEDIATING → RESOLVED / MANUAL.

Technical Architecture

Stack

  • Compute: FastAPI (Python 3.11) on Operative platform (port 8001)
  • Storage: PostgreSQL — alert_reports (uploaded data), incident_management.incidents (ticket pipeline), agent_config (settings)
  • Classification: Rule-based noise detector (noise_detector.py) with configurable thresholds
  • Data Sources: OpsGenie API (standalone + cloud), Atlassian JSM, file upload (JSON/CSV)
  • Optional backends: Redis (cache), Vector DB (embeddings for RAG), Neo4j (graph) — configured via env

Noise Classification Rules

Alert Analyser uses rule-based scoring to classify alerts as NOISE, GENUINE, or SUSPECT. The scoring function sums points for each rule:

+2
Alert fires more than 3 times within 1 hour (high repeat rate)
+2
Alert auto-closes in less than 5 minutes without acknowledgement
+1
Alert was never acknowledged (no human interaction)
-3
Priority is P1 or P2 (high severity overrides noise signals)
-2
Alert open more than 30 minutes (active issue, not noise)
Threshold
NOISE if net score > 0 · Otherwise GENUINE

Key Features

  • Dedup key: alert_id (not alert_signature) — same alert across multiple sources is one ticket
  • Recurrence: If alert_id fires again during remediation, bumps recurrence_count on existing ticket
  • Related tickets: Links new ticket to prior resolved ticket for same alert_id for pattern tracking
  • Auto-reconciliation: Stale ESCALATED tickets auto-resolved when alert clears in source system
  • Manual fallback: If no automation available, ticket remains MANUAL for human triage

Key Business Outcomes

  • Reduces alert fatigue: Noise alerts identified and suppressed before reaching on-call engineers. Team productivity improves immediately post-deployment.
  • Automated ticket creation: Genuine alerts create traceable incident tickets without manual intervention. Eliminates "who created this ticket?" visibility gap.
  • SLA visibility: Real-time aging panel shows which tickets are breaching response targets. Enables priority-aware work queueing.
  • Recurrence detection: Tickets that re-fire during remediation are surfaced immediately. Fix validation catches broken patches in minutes, not days.
  • Audit trail: Full alert_payload preserved in ticket for RCA teams. Enables forensic analysis and pattern discovery after resolution.
  • Future-ready: incident_management schema is shared with planned RCA and Action agents via polling model. New agents can be added without data model changes.

Incident Ticket Purge

Stale ESCALATED tickets with no downstream action are purged on a configurable schedule to prevent unbounded growth and enforce SLA discipline.

Purge Behaviour

  • Tickets are not deleted — status is set to PURGED with purged_at timestamp and purge_reason for full audit trail
  • Only ESCALATED tickets older than the configured threshold are eligible
  • PURGED tickets are excluded from all active views (pipeline flow, kanban, aging, SLA breach)
  • Default threshold: 7 days — configurable in Settings → Incident Mgmt
  • Purge reason format: SLA_BREACH_NO_ACTION_{N}D where N is the configured days

Purge Controls

  • Dry Run — shows count of eligible tickets by priority without making changes
  • Run Purge — executes purge (requires "Enable automatic purge" to be checked in settings)
  • Purge Audit — full history queryable via DB: SELECT * FROM incident_management.incidents WHERE status = 'PURGED' ORDER BY purged_at DESC

Pipeline Context

Purge enforces SLA pressure on the downstream pipeline. When RCA and Remediation agents are active, tickets must be processed within the threshold or they will be purged. This prevents stale tickets accumulating indefinitely while downstream agents are under development.
