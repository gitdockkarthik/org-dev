1. The Agent Contract

Any agent — Python, Java, Node.js, Go, anything — needs to expose exactly three HTTP endpoints. The portal routes all traffic through these. Nothing else is required.

GET
/health
Returns agent liveness. Portal uses this to confirm the agent is reachable before routing chat messages.
{"status": "ok"}
POST
/invoke
Receives a chat message, returns a complete response. Used for non-streaming interactions.
← session_id, user_message,
   history, context
→ {session_id, response}
POST
/invoke/stream
Same input as /invoke but returns an SSE stream. Each chunk is a data: event.
← same input
→ data: chunk


→ data: [DONE]

2. Build and Run the Agent

For this demo we built a minimal Echo Agent in Python — 50 lines, no database, no external dependencies beyond FastAPI. It runs in its own Docker container on port 8004, completely independent of the portal stack.

# docker-compose.yml — standalone, no portal dependency
services:
  echo-agent:
    build: .
    ports: ["8004:8004"]
    restart: unless-stopped

# Build and run
docker-compose up -d --build

# Verify health
curl http://localhost:8004/health
→ {"status":"ok","agent":"echo-agent"}
Key principle: The agent has no knowledge of the portal. It just runs on a port and responds to HTTP requests. The portal discovers it via the Invoke URL registered in the next step — loose coupling by design. Any language or framework that can serve HTTP works.

3. Register in the Portal

Navigate to Admin → Agent Registry → + Register Agent. Fill in the agent's name, slug, and invoke URL. The agent starts in Draft status and can be published immediately.

kpi-internal.cloud.operative.com:3000/admin/agents/register
POST /api/registry/agents
{
  "name":        "Echo Agent",
  "slug":        "echo-agent-v2",
  "description": "Dummy agent for portal registration testing",
  "version":     "0.1.0",
  "invoke_url":  "http://kpi-internal.cloud.operative.com:8004"
}
→ Agent registered. Status: draft.

8. LLM Integration Options

External agents have three options for LLM access. Choose based on your deployment context.

Option 1 — Self-managed LLM Credentials Available

Agent team manages their own LLM credentials via .env. No UAP dependency.

a) Anthropic Direct

Generate your API key at console.anthropic.com.

ANTHROPIC_API_KEY=sk-ant-...
LLM_MODEL=claude-sonnet-4-6

b) AWS Bedrock (IAM access key pair)

Requires the Anthropic SDK's Bedrock client (AsyncAnthropicBedrock) — a code dependency, not just configuration. The SDK resolves credentials from env vars automatically.

LLM_PROVIDER=bedrock
LLM_MODEL=us.anthropic.claude-sonnet-5
AWS_REGION=us-east-1
AWS_ACCESS_KEY_ID=AKIAW*****
AWS_SECRET_ACCESS_KEY=F9***

Verify connectivity before configuring your agent:

curl -sS -X POST \
  "https://bedrock-runtime.us-east-1.amazonaws.com/model/us.anthropic.claude-sonnet-5/invoke" \
  -H "Authorization: Bearer <your-bedrock-api-key>" \
  -H "Content-Type: application/json" \
  -d '{"anthropic_version":"bedrock-2023-05-31","max_tokens":100,"messages":[{"role":"user","content":"Say hello."}]}'

Option 2 — UAP-managed LLM In Progress

Agent calls UAP's token vending endpoint using the platform's BACKEND_API_KEY. The raw LLM key never leaves UAP. Requires code changes in the agent backend to call the gateway instead of the LLM SDK directly.

UAP_URL=https://<uap-platform-url>
BACKEND_API_KEY=<provided by platform team>
# Step 1 — Fetch short-lived token (5 min TTL)
POST /api/llm/token
Headers: X-API-Key: <BACKEND_API_KEY>
Body:    {"agent_slug": "your-agent-slug"}

# Step 2 — Proxy LLM call
POST /api/llm/invoke
Headers: X-API-Key: <BACKEND_API_KEY>
Body:    {"token": "<token>", "messages": [...], "system": "..."}

See agents/mock-agent/llm_gateway.py for a reference implementation with automatic fallback to Option 1 when UAP is unavailable.

Option 3 — Self-service Agent Keys Planned

Agent owners generate their own scoped API key from the UAP portal (Developer Settings) — no platform team involvement. Key is per-agent, revocable, and decoupled from registration.

  • New "Developer" role in UAP RBAC
  • Self-service key generation UI in portal
  • Keys stored encrypted in UAP DB, per-agent scoped
  • Switching from Option 2 → 3 requires only replacing BACKEND_API_KEY with UAP_AGENT_KEY — minimal code change

9. Registration — New Fields

The registration and edit forms now include two new fields:

  • Landing Page URL — For externally-built agents. Shows a "Launch Agent" button on the catalogue card opening the agent's own UI in a new tab.
  • Use UAP-managed LLM — Toggle. When enabled, the agent is expected to call the UAP token vending API instead of holding its own LLM credentials. Stored as uses_uap_llm on the agent record.

10. Mock Agent — Reference Implementation

A working mock agent (mock-agent, port 8099) demonstrates the full UAP LLM gateway pattern:

  • No LLM API key stored — calls /api/llm/token then /api/llm/invoke
  • Own chat UI at /static/chat.html — registered as Landing Page URL
  • Registered with uses_uap_llm=true — shows UAP-managed LLM badge
  • Catalogue card shows: Stand-alone badge + Launch Agent button (no Chat button — chat is inside the agent's own UI)
